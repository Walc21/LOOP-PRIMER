## 2024-10-23 - JSON Schema Validator Caching
**Learning:** `jsonschema.Draft202012Validator` initialization is relatively expensive (around 0.2ms - 3ms depending on schema complexity). It is used heavily in `article-loop` (22 instances), and because it takes an arbitrary dictionary (which isn't directly hashable in Python), caching is missed.
**Action:** When working with JSON schema validations that happen in loops or hot paths, cache the validator instances using `functools.lru_cache` and `json.dumps(schema, sort_keys=True)`. Using an object ID (`id(schema)`) lookup table in combination with the string hash cache makes it exponentially faster for identical dictionary instances.

## 2024-10-24 - Over-optimizing ast.walk
**Learning:** `ast.walk` has some overhead in large files because it dynamically queries `iter_fields` and `iter_child_nodes`. Replacing it for performance can yield a 30-40% speed up in parsing, but writing manual traversals correctly is hard and prone to missing nested block constructs (like `orelse`, `handlers`, nested functions). A regex-based approach for tasks like "counting test definitions" is significantly faster and less fragile than custom AST traversal logic, or using a subclassed `ast.NodeVisitor` is the safer canonical way if you absolutely need AST.
**Action:** Do not sacrifice readability or robustness to eliminate `ast.walk` overhead without a proven overall application bottleneck. If standard AST tools are "slow," use regex for simple token-based analysis, or use `NodeVisitor`, but do not attempt shallow loops over `tree.body`. Always make sure no scratch files are left behind.
